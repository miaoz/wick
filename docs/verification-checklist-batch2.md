## T4-1 · Dropbox 双设备 sync v2 真实回归

**前置**：两台设备（Mac+iPhone 或两台 Mac）登同一 Dropbox 账号，都开启 Wick 同步（app 包内）。

**逐场景操作**（每步后把同步日志发我）：
- [ ] **推**：设备 A 新建日记并打字 → B 同步后出现（拉取即定点：B 收到后不再重复推回）。
- [ ] **拉/改**：B 修改同一天 → A 同步后收到，rev 回声抑制（A 不因自己的 rev 变化再推）。
- [ ] **冲突**：A、B 在同步间隔内各自改同一条 → 冲突归档到 `conflicts/`，合并结果合理，无数据丢失。
- [ ] **删除传播**：A 删除整个日记本 → B 同步后本地也删除；远端 manifest/目录被清。
- [ ] **墓碑 GC**：删除超过保留期后远端墓碑被清理，被删日记本不会复活成「可导入」。

**通过标准**：三不变量成立——无自冲突、拉取即定点、rev 回声抑制；`WickSyncTests` 假后端场景与真机表现一致。

## T4-5 · Instruments 万条级大库实测（2026-08-29 已实测，发现一处疑似现存 bug）

**万条 zip**：`scripts/gen_large_journal.py` 生成（200 天 × 50 条 = 10000 条，0.5 MB），已实测导入/加载/搜索并清理。

**数据层（真实 `JournalStore` 代码）**：导入 0.26s；全文搜索「交易」0.17s（冷）/0.16s（暖）；「第 4」0.28s；持久化 0.11s；重载 0.27s；正文驻留 ~14.8 MB。无病态。

**真实 App（打包版 v1.10.31）界面实测**：
- 万条本全量命中搜索（「交易」10k 条）：扫描期 CPU ~100% 短暂、RSS +311MB（311→622MB，清除后仍 ~665MB）—— 10k 结果数组驻留，有界但偏大。
- **发现疑似现存 bug：日记窗口打开即持续 ~31–33% CPU**。`sample` 定位为 `NSHostingView.layout` 被每个 display cycle 强制调用（`CA::Transaction::commit → NSDisplayCycleFlush → layoutIfNeeded → NSHostingView.layout` 每帧循环）。对照：仅菜单栏（窗口关）= **0.0% CPU**；打开日记窗口（任意本、任意天）= ~32%。该行为存在于**已安装的 v1.10.31 打包版**（与本次源码改动无关）。疑似与 AGENTS「窗口 hosting view 布局自生长」条目相关，或由窗口内实时元素（今日已过百分比/烛痕条）每帧失效触发。
- 测试后已删除「性能测试」本并恢复 catalog（active 回到手工交易）。

**若修**：需在源码定位窗口宿主视图的持续失效源（先对照 AGENTS 日记窗条目），重建 + 重装 .app 后复测。

- [ ] Time Profiler：连续侧栏切换 / 搜索 / 打字，确认渲染路径不读盘（侧栏统计走失效缓存、
      Lightbox 全图一次入 `@State`）。
- [ ] 同步一轮：Allocations 看内存峰值平稳，无随库大小线性攀升。

**通过标准**：渲染路径无磁盘 IO；同步轮内存峰值平稳。
